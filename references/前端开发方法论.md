# 前端高级开发工程师方案产出指南 · 领域方法论

> 本文档是 `frontend-dev-guide` 技能的领域知识库。

---

## 一、场景识别

| 场景 | 名称 | 判断条件（满足任一） | 产出量 | 预估周期 |
|------|------|---------------------|--------|---------|
| 场景一 | 0→1 新前端项目 | 全新项目、需从技术选型开始、涉及项目脚手架搭建、需定义整体架构 | 10-12类 | 3-6周 |
| 场景二 | 中大型功能开发 | 已有项目新增模块、涉及3+页面/组件、需新路由+状态管理+API对接 | 6-8类 | 1-3周 |
| 场景三 | 小优化/Bug修复 | 单组件修改、单Bug修复、小范围重构 | 2-3类 | 1-3天 |
| 场景四 | 大版本技术升级 | 框架迁移(如Vue2→Vue3)、构建工具升级(Webpack→Vite)、涉及全局变更 | 8-10类 | 2-6周 |
| 场景五 | 技术预研/选型 | 新技术评估、PoC验证、方案对比 | 3-4类 | 1-2周 |

### 识别流程

```
是否全新项目/无技术基础？ → 是 → 场景一
    ↓否
是否框架迁移/大版本技术升级？ → 是 → 场景四
    ↓否
是否为技术评估/PoC？ → 是 → 场景五
    ↓否
是否涉及3+页面/新路由/新状态模块/新API对接？ → 是 → 场景二
    ↓否
→ 场景三
```

## 二、场景一：0→1 新前端项目（12类产出）

### 调研与选型阶段
1. **技术调研报告** — 候选框架/库对比（React vs Vue vs Svelte vs Solid）、兼容性分析（浏览器/Node版本）、团队技术栈匹配度
2. **技术选型方案** — 最终技术栈决策（框架/构建工具/状态管理/路由/UI库/请求库/测试框架/类型系统）、选型理由、风险评估

### 架构设计阶段
3. **项目架构设计** — 目录结构设计、代码分层（pages/components/hooks/services/utils/types）、模块化方案、Monorepo决策
4. **组件架构设计** — 组件树（页面→容器组件→展示组件→基础组件）、组件通信模式（props/context/store/event bus）、组件复用策略
5. **状态管理方案** — 全局状态 vs 局部状态划分、Store结构设计、数据流方向、持久化策略
6. **路由设计** — 路由表定义（含嵌套/动态路由）、权限路由/路由守卫、懒加载策略、页面转场

### 基础设施阶段
7. **工程化配置** — ESLint/Prettier/Husky/lint-staged、TypeScript配置、环境变量管理、CSS方案（Tailwind/CSS Modules/CSS-in-JS）
8. **API对接规范** — 请求封装（拦截器/重试/缓存）、错误码统一处理、数据转换层（DTO→VO）、接口Mock方案
9. **性能方案** — 打包优化（代码分割/Tree Shaking）、加载优化（懒加载/预加载/骨架屏）、渲染优化（虚拟列表/memo/防抖节流）、缓存策略（Service Worker/CDN/HTTP缓存）、Core Web Vitals指标目标（LCP<2.5s/FID<100ms/CLS<0.1）

### 质量保障阶段
10. **测试策略** — 测试金字塔（单元60% / 集成30% / E2E 10%）、测试工具选型、组件测试规范、关键路径E2E
11. **CI/CD配置** — 代码检查→测试→构建→部署流水线、环境拆分（dev/staging/prod）、回滚方案
12. **可访问性方案** — ARIA标签规范、键盘导航、焦点管理、屏幕阅读器适配、色对比度、语义化HTML

## 三、场景二：中大型功能开发（6-8类产出）

1. **功能需求分析** — 功能背景、用户场景、技术要求、依赖分析
2. **组件树设计** — 组件拆分方案、父子组件关系、Props/State/Events定义
3. **数据流设计** — 该功能的状态归属（局部/全局）、API调用链路、数据更新与消费
4. **路由设计** — 新路由定义、参数传递、页面转场
5. **接口对接方案** — 请求/响应类型定义、错误处理、Loading/Empty/Error状态组件
6. **状态机设计** — 交互状态流转图（含异常处理）、各类状态对应的UI表现
7. **性能评估** — 是否引入新依赖、渲染性能影响分析、bundle体积预估
8. **测试用例设计** — 单元测试覆盖、组件测试(Snapshot/交互)、关键路径E2E

---

## 四、场景三：小优化/Bug修复（2-3类产出）

1. **问题分析** — Bug复现步骤、根因分析、影响范围评估
2. **修复方案** — 代码改动说明、边界情况考虑、性能影响
3. **回归测试清单** — 关联功能检查、多端/多浏览器验证

## 五、场景四：大版本技术升级（8-10类产出）

1. **升级评估报告** — 升级动机、收益分析、Breaking Change清单、工作量评估
2. **兼容性分析** — 浏览器兼容性、依赖库兼容性、第三方SDK兼容性
3. **渐进式迁移方案** — 分阶段迁移计划、新旧代码共存策略、双构建/双运行方案
4. **技术方案设计** — 新架构vs旧架构对比、迁移后的目录结构、API变化对照表
5. **代码迁移指南** — 逐模块迁移checklist、自动化迁移脚本（jscodeshift/codemod）、常见迁移陷阱与解决方案
6. **性能基准对比** — 新旧构建产物对比（体积/加载时间/运行时性能）
7. **灰度发布方案** — 灰度策略（百分比/人群/地区）、监控指标、回滚条件
8. **测试策略** — 视觉回归测试、功能回归测试、性能回归测试
9. **团队培训计划** — 技术分享Slide、代码示例对照、最佳实践文档
10. **回滚预案** — 触发条件、回滚步骤、数据兼容性

## 六、场景五：技术预研/选型（3-4类产出）

1. **技术调研报告** — 候选方案介绍、社区活跃度（GitHub Star/Issue/Release频率）、团队匹配度

## 七、前端通用规范

### 组件设计规范
- 单一职责：一个组件只做一件事
- Props向下，Events向上
- 优先组合而非继承
- 容器组件负责数据获取与状态管理，展示组件只负责渲染
- 每个组件必须考虑：default / loading / empty / error 四种状态

### CSS方案决策树
```
是否需要Utility-First快速开发？ → 是 → Tailwind CSS
是否需要组件级样式隔离？ → 是 → CSS Modules / CSS-in-JS
是否需要全局样式系统？ → 是 → SCSS + CSS Variables
```

### 性能KPI目标
| 指标 | 目标值 | 测量工具 |
|------|--------|---------|
| LCP (Largest Contentful Paint) | < 2.5s | Lighthouse / Web Vitals |
| FID (First Input Delay) | < 100ms | Web Vitals |
| CLS (Cumulative Layout Shift) | < 0.1 | Web Vitals |
| TTI (Time to Interactive) | < 3.5s | Lighthouse |
| Bundle Size (JS) | < 200KB (gzip) | webpack-bundle-analyzer |
| Lighthouse Score | > 90 | Lighthouse |

### TypeScript 类型安全等级
- Level 1：关闭 `noImplicitAny`（快速原型）
- Level 2：开启 `strict: true`（推荐）
- Level 3：开启 `strict: true` + 禁止 `any`（类型极致安全，大型项目）

### 浏览器兼容策略
| 项目类型 | 最低支持 | Polyfill策略 |
|---------|---------|-------------|
| 内部管理系统 | 最新2个版本 | 无 |
| 对外C端产品 | iOS Safari 14+, Android Chrome 90+ | 按需（core-js） |
| 政务/金融 | IE11（如必需） | 全量polyfill + 降级方案 |

## 九、产出质量检查清单

### 通用检查
- [ ] 场景判断正确并已确认
- [ ] 产出清单完整
- [ ] 技术决策有清晰的理由和权衡

### 代码质量
- [ ] 组件职责单一、Props/Events清晰
- [ ] default/loading/empty/error 四种状态有处理
- [ ] TypeScript类型完整、无 `any` 滥用
- [ ] Lint检查通过、代码格式一致

### 性能
- [ ] 大列表使用虚拟滚动
- [ ] 图片使用懒加载、合适格式（WebP/AVIF）
- [ ] 代码分割合理、无单文件过大
- [ ] 无明显的内存泄漏（useEffect cleanup、事件解绑）

### 安全
- [ ] XSS防范（不使用dangerouslySetInnerHTML/v-html或不信任内容经消毒）
- [ ] 敏感信息不暴露在前端代码中
- [ ] HTTPS强制
- [ ] CSP头配置

### 测试
- [ ] 关键业务逻辑有单元测试
- [ ] 关键组件有Snapshot + 交互测试
- [ ] 关键用户路径有E2E测试

### 可维护性
- [ ] 目录结构清晰
- [ ] 命名有意义、风格一致
- [ ] 关键逻辑有注释
- [ ] 文档（README/组件的Storybook）齐全
